CHOSEN-ONE / MAP

Under the Hood

How does this portfolio work?

Architecture

There is no framework and no game engine here. The whole thing is one <canvas> element, one JavaScript file, and a fixed 60 Hz accumulator loop — about 900 lines with no dependencies at all.

The split is simple: the canvas draws the world, and ordinary DOM sits on top of it for anything made of text. Menus, dialogue and these panels are HTML, which means they get real fonts, real links and real accessibility for free, while the game underneath stays a pure pixel surface.

State lives in three places — a stage table describing the world, a player object, and a small amount of transition state. That's the entire model.

Stage System

Most 2D games build levels from a tilemap and a collision mesh. This one doesn't have either. Each painted image is a stage, exactly one screen wide, and the ground is part of the artwork.

So a stage needs only a few numbers: where the feet sit (feetY), how zoomed the art is (scale), and how far the solid ground reaches (x0 and x1). Walk past x1 and the screen fades to the next stage; walk past x0 and it fades back.

Every one of those numbers was measured against the characters already painted into the scene, so the hero stands on the same ground they do and matches their height. That's why the zoom differs per stage — the source images were shot at wildly different scales, from 1.2× to 3.0×.

Rendering

The canvas is backed at real display resolution — viewport × devicePixelRatio — and the 512×288 design space is mapped onto it with a single transform. Drawing code works in design coordinates while every pixel it produces is an actual screen pixel.

That matters more than it sounds. The naive version draws into a fixed 512×288 buffer and lets CSS stretch it, which crushes a 1280px painting to 512 and blows it back up — throwing away 60% of the detail and then magnifying what's left.

Filtering is chosen per draw, from the direction of scaling: smoothing on when an image is being shrunk, off when pixel art is being enlarged. Nearest-neighbour is right for one and actively destructive for the other.

Animation

Several stages are animated. The obvious approach — drop an animated GIF in an <img> and blit it each frame — does not work reliably: browsers only advance GIF frames while the page is actively painting, so a clipped, backgrounded or merely unlucky image freezes on frame one.

Instead each animated stage is decoded once with WebCodecs ImageDecoder into a set of ImageBitmaps, and played from the game clock. Timing is under our control and the result is identical everywhere.

The character is a different problem: an 800×448 sheet of 80×64 frames, composited at build time from six separate paper-doll layers — skin, hair, shirt, trousers, boots — into a single texture. The art faces left, so facing right is the mirrored case.

NPC System

Most of the people you can talk to were already painted into the artwork. Rather than draw new sprites over them, each is just a trigger point at that figure's x position. Two stages had nobody standing in them, so those get a villager composited from the same paper-doll layers as the hero.

Proximity is nearest-wins, not first-in-range. On a crowded screen with five people standing close together, "is anyone in range?" would let whichever one appears first in the array hold the floor while you walk past the other four.

Nobody is solid. A villager standing mid-stage would otherwise wall off the only route onward — and since the hero draws on top, walking past reads correctly as passing in front of them.

Optimization

Decoded animation frames are the only real memory cost, so they're bounded on three axes: a frame budget per stage (larger frames mean fewer of them), a decode resolution matched to the display rather than the source, and an LRU cache holding only a few stages at once.

Decoding is lazy and predictive — the current stage plus its neighbours, so the next screen is ready before you reach it.

An IntersectionObserver pauses the loop entirely when the canvas scrolls out of view, and the fixed-timestep accumulator clamps large deltas so a backgrounded tab doesn't return and simulate thirty seconds in one frame.
